# 微信「内容结构检测」排查记录

## 结论与证据边界

截图中的风险是 `line-height-overlapping`（行高小于字体大小、多行文字可能重叠）。需要区分三件事：

1. **真实排版错误**：如正文 15px 字号配 8px 行高、多行文字确实交叠。应该修 CSS，不能忽略。
2. **行内片段导致的测量误报**：正文看起来只有一行，但 `Range.getClientRects()` 会为文字、`strong`、`code` 等返回多个矩形。矩形数量不能直接当行数。
3. **Markdown 自动转换提示**：剪贴板的 `text/plain` 原来传的是 Markdown 源码，与 `text/html` 不一致。这和叠字告警不是同一个问题；现已改为渲染后的可读正文，但正文自身包含 Markdown 代码时仍可能触发识别。

项目既有的后台追踪记录（70 个块）与下式吻合：

```text
bbox = max(rect.bottom) - min(rect.top)
疑似风险 = bbox / rects.length < 0.95 * fontSize
```

这是**未包含候选节点筛选的历史观测模型**，不能单独用来判定违规。后续已从历史真机调用栈取得公开前端脚本，确认其中一个分支使用类似公式，但先筛选直接含非空白文本的指定标签（见下节）。用户确认简洁模式不弹窗后，旧保色模式实际仍有 44 条告警；2026-10-01 用户反馈当前修订在本次后台复验中看起来未再弹出结构警告，尚无新的采集报告，也未确认外观与保存后的手机预览。开源 CLI、历史模型、版本化脚本子集和实际弹窗必须分别记录。

## 保色独立采集与本次修正（2026-10-01）

`wechat-diagnostic (2).json` 第 1 阶段标记为「保色」，输入为 LitePan 文章：HTML 60,890 字符、纯文本 3,488 字符，17 个 strong、108 个 span、3 个 a、17 张图片。实际弹窗解析到 **44 条行高告警、0 条宽度告警**。不要把临时标记或本地模型命中数当作这个数字。

证据限制：

- 120 条段落证据仍在，但有效布局样本只有空编辑区的 8 字占位内容，`quality=insufficient`。旧扫描器跳过了 `visibility:hidden` 的检测沙箱，而它实际有布局；新探针对带段落标记的隐藏副本开放测量，仍排除 `display:none` 和已脱离文档的节点。
- 同一段号可能写在段落和多个子标签上。旧探针用最后一个子标签覆盖整段，不能据此认定「span 本身就是被告警节点」；新探针优先保留同段号最外层节点。
- 8 个告警段号（43、46、53–56、81、84）结合**先前简洁报告**对应 shell 命令，其余 36 个对应正文混排。这是跨报告定位，不是本次捕获了完整 HTML。
- 17 张图的检测副本样式均出现 `width:100px`。下述公开脚本的未加载图片兜底会把 `parseFloat('100%')` 当作 100，再写回 px，与此现象吻合；不证明实际编辑区图片也是 100px，也不能仅凭零宽度弹窗认定图片已全面解决。本轮没有再改动图片 CSS。

### 找到缺失的候选筛选条件

从历史真实调用栈对应的[公开前端脚本 4da8090c](https://res.wx.qq.com/mpres/zh_CN/htmledition/js/default~media/appmsg_edit_v2_gray~media/get_article_structure_tmpl_fe.4da8090c.js)提取了 `Ir/De` 分支：

1. 只遍历根节点的后代；标签在 `p/div/section/h1–h6/li/td/a` 中。
2. **必须直接含有非空白文本节点**，不是只要后代有文字就检查。
3. `Range.selectNodeContents` 后只保留高度大于 0 的矩形；取 `Range.getBoundingClientRect().height`。
4. 计算行高为 0，或矩形数至少 2 且「总高度 / 矩形数 < 字号 × 0.95」时报告重叠。

因此，`<p>通过 <strong>SSH</strong> 登录</p>` 可能误报，`<p><span style="color:#000">通过 <strong>SSH</strong> 登录</span></p>` 则不进入此分支的段落候选。这也解释了为什么不能推断「所有行内标签都会报错」，以及为什么旧模型命中 125 次不代表实际弹窗有 125 条行高告警。

当前保色模式对安全的纯行内混排内容统一增加显式保色的文本 span，保留原有子节点、链接、配色、缩进与字号/行高，不伪造文字、不增加忽略检测属性。纯文本段落、纯色代码行保持原结构，图片或块级后代不会被强行塞进 span。原样及简洁模式不变。

`tools/wechat-bundle-line-height.mjs` 可离线复现**这一版本的这一分支**；`capturedBundleFallback` 与原来的 `suspected` 分开记录。该分支甚至会漏掉某些真实低行高问题，因此独立的 CSS/几何风险检查继续保留。来源是历史调用栈，不是本次 JSON 内捕获的脚本版本；不能宣称已复现整套或当前版本的微信检测器。

本地回归覆盖三个宽度下旧保色混排命中 → 修订后此分支零命中，逐字符颜色/粗细/斜体、段落尺寸、可读文字、代码缩进及剪贴板一致。`docs/test.md`（Candlr，不是本次 LitePan）在 375/585/677px 的保色输出均为此分支 0 命中；外链资源禁用造成图片待核查，不能拿离线图片结果作后台结论。

## 简洁模式独立采集结果（2026-10-01）

v3 报告的简洁阶段输入含 17 张图片，`strong/em/code/pre/span/a` 计数均为 0；捕获到 125 个正文块和实际检测弹窗。弹窗为 **0 条行高告警、1 条图片宽度告警**。本地历史片段模型却命中 125 个块，因此不能用该模型数量代替微信告警数。此结论仅适用于该次文章/输入，不代表所有文章通过。

剩余图片的检测副本含 `width:596px;height:594.987px;max-width:100%`。官方 1.4.3 说明固定宽度可能在不同屏幕下产生宽度占比差异。原来仅设置 `max-width:100%` 会让图片在窄屏缩小、宽屏停在固有宽度；简洁模式现改为明确的 `width:100%;height:auto`，保持相同占比并保留固有比例。小图放大是该模式的视觉代价，原样排版不变。

本地使用 596×595 测试图验证 375/585/677px 容器及复制结果；**用户随后反馈修复后的简洁模式不再弹出告警**；尚无新的 DOM 采集报告说明平台是否再次改写尺寸，也不能把这个结果推广到其他文章或保色模式。不对图片批量添加 `data-ignore-width` 来隐藏检查。

## 最小复现（不包含用户文章）

将下面两段放到浏览器中。二者都是字号 15px、行高 27px 的单行文字，视觉上没有叠字，第二段仅增加局部加粗。

```html
<p id="plain" style="font-size:15px;line-height:27px">通过 SSH 登录。</p>
<p id="styled" style="font-size:15px;line-height:27px">通过 <strong>SSH</strong> 登录。</p>
```

在开发者工具运行以下代码，观察片段数与估算值的差别：

```js
for (const id of ['plain', 'styled']) {
  const el = document.getElementById(id);
  const range = document.createRange();
  range.selectNodeContents(el);
  const rects = [...range.getClientRects()];
  const bbox = Math.max(...rects.map(r => r.bottom)) - Math.min(...rects.map(r => r.top));
  const fontSize = parseFloat(getComputedStyle(el).fontSize);
  console.log(id, {
    fragments: rects.length,
    estimatedLineHeight: bbox / rects.length,
    threshold: fontSize * 0.95,
    rects: rects.map(r => ({ top: r.top, height: r.height, width: r.width })),
  });
}
```

要验证**微信后台是否仍存在同类行为**，必须把这两段分别复制到两篇空白草稿对照测试。只在本地运行上面的模型不能证明后台当前算法。向平台反馈时附上这两段、浏览器版本、检测时间及告警截图即可，无需公开整篇私人文章或账号信息。

## 本次提供的处理路径

### 原样排版（默认）

保留现有主题、链接、局部强调、代码高亮和 Mac 三点。不因疑似误报放大行高、不偷偷删除内容。若后台继续告警，应先看定位段落及手机预览，确认是否真实叠字，再决定是否继续插入。

### 保色排版（实验）

简洁模式通过本次用户文章检查后，用户反馈原有配色丢失。新增独立的「保色排版」供外观与结构之间对照，**不覆盖、不改动已验证的简洁模式输出**，默认仍为原样。

- 恢复原主题的橙红强调色、加粗、斜体、灰色删除线、蓝色可点击链接和 Atom One Dark 逐词代码高亮。
- 标题样式放到标题本身，保色 H2 黑底随文字宽度收缩、长标题在正文宽度内换行；列表去掉多余 section；代码保留 Mac 三点、原有内边距及暗色圆角阴影，正文不用 pre/code，仍为段落行。
- 单色代码行直接给 p 上色，多色行的 token 平铺，混排裸文本由一个保色文本 span 统一承载；保留真实空行、NBSP 缩进、制表符展开及 HTML 转义。
- 行内代码保留底色、等宽字体和强调色，改用 span；恢复原样模式的 14px 字号、25px 行高及内外留白，保留混排归一化结构。
- Markdown 图片与简洁模式一样使用 `width:100%;height:auto`，小图可能放大。

**旧保色版已实测出现 44 条行高告警；2026-10-01 用户反馈当前修订看起来未再弹出结构警告。该结果仅代表本次手动测试，不保证所有文章通过。** 保色依然依赖行内标签，平台粘贴后的清洗可能再次改变结构。浏览器测试能确认配色、文字、结构和复制一致，不能证明微信会接受。原始 Markdown 不变，随时可切回简洁或原样。

### 简洁排版（实验）

在预览区顶部的「排版」下拉菜单选择。预览和复制用同一份内容；切回原样即可恢复，Markdown 源文不变，刷新后默认仍为原样。

| 内容 | 简洁模式的变化 |
| --- | --- |
| 加粗、斜体、行内代码 | 文本保留，去掉局部强调和行内标签 |
| 删除线 | 显示 `〔已删除：原文〕`，避免被误认为正常正文 |
| 链接 | 变为 `文字（网址）`，纯网址不重复，**不可点击** |
| 标题 | 样式放在标题本身，H2 黑底铺满一行 |
| 代码块 | 去掉高亮和 Mac 三点，保留深色底、等宽字体、空行及缩进；每行是直接含文字的段落，空格用 NBSP，Tab 展开为 4 空格 |
| 列表、引用、表格、图注 | 保留结构 |
| Markdown 图片 | `width:100%;height:auto`，按所在正文宽度等比显示，**小图可能放大**；加载后仍写入真实 `data-w` / `data-ratio`，不伪造尺寸、不增加宽度豁免 |

这是一项**有视觉代价的结构降级**，不是全量 HTML 清洗或官方认证的「安全模式」。表格、图片、手写 HTML、硬换行等复杂结构仍可能出现其他告警；原生 HTML 不会被这个模式统一改写。代码从 `pre/code` 改成段落后在微信粘贴、保存时的表现也需要人工核验。

### 本地自动 A/B 对照（不需要登录）

```bash
npm run diagnose -- --markdown article.md
npm run diagnose -- --html article.html
```

- Markdown 模式自动渲染「原样 / 保色 / 简洁」三种排版，每种分别量测 375、585、677px。
- HTML 模式直接量测导出的 HTML，不运行 HTML 中的脚本和事件处理器。
- 默认禁用所有外部网络资源，因此外部图片未加载、外部样式缺失要在后台再次核验。Markdown 中的手写 HTML 会被转义，避免执行不可信内容；需要检查这些 HTML 的真实布局时，请使用 `--html`。

### 微信后台只读探针（一次粘贴，自动采集）

```bash
npm run diagnose -- --probe
```

生成 `reports/wechat-console-probe.js`，源代码位于 `tools/article-diagnostics.mjs`，没有网络请求、正文写入、保存或发布操作。

1. 打开微信文章编辑器中的新空白草稿，**在粘贴文章之前**按 F12 打开开发者工具的 **Console**，粘贴生成的脚本并运行。旧报告的段号无法从再次打开弹窗自动恢复。v3 支持一次运行内按多次粘贴分组，但 A/B 对照仍应使用空白正文，避免两种内容叠加。
2. 在 90 秒内复制粘贴文章并触发「内容结构检测」，尽量保持告警弹窗打开。脚本自动扫描正文、同源 iframe 和临时离屏副本，记录临时段落标记及检测弹窗文字。若检测阻止插入，正文编辑区可能尚无文章；此时以临时副本证据为准，不能把空编辑区的 0 风险当作通过。
3. 90 秒后自动停止并输出表格。运行 `__md2wxDiagnostic.download()` 下载 `wechat-diagnostic.json`；也可提前下载，下载会先停止并完成最后一次采集，避免导出中间快照。请注明各次粘贴使用“原样”“保色”还是“简洁”排版。

报告会保留微信 `data-blockidx` → 「第 N 段」的映射。v3 报告包含：

- `phases`：按每次用户粘贴事件自动分组。第 0 组是运行脚本时的既有页面，后面分别是“粘贴 1”“粘贴 2”……；每组独立保留时间、输入摘要、正文、段号和弹窗告警，不再把两次结果合并成一份判定。
- `paste`：本次输入的 HTML/纯文本长度、非加密指纹、近似标签计数和短摘录，不保存完整 HTML，也不修改或拦截粘贴。这能区分“简洁输入”与“编辑区仍包含上一次原样内容”。
- 每个阶段保存各正文容器/宽度的**最新**样本，不再按“命中项更多”保留旧样本；嵌套临时节点合并扫描，不再为每层父节点占用一份快照额度。
- 顶层清单只用于汇总，`quality` 描述最后一组；判断 A/B 应查看各组自身的 `quality` 和 `officialWarnings`，不能将汇总的 37 条当作最后一次结果。

- `officialWarnings`：从检测弹窗文字解析的实际告警段号/类型，与扫描器的 `findings` 分开，不混为一谈。
- `root`：每个候选正文的标识、文本长度和短摘录，用来识别误选标题或占位区。
- `quality`：采集质量提示。`insufficient` 表示未采到足够正文；`partial` 表示映射缺失、无法访问部分页面等；`captured` 仅描述采集状态，不表示微信检测通过。
- `root.hiddenLayoutIncluded`：标记是否允许测量带临时段号的隐藏检测副本；隐藏不等于没有布局，脱离文档或 `display:none` 仍不测量。
- `paragraphEvidence`：同段号优先保留最外层节点，避免子 span 覆盖整段。临时段号对应的短摘录、局部样式和图片数量/尺寸属性（不记录图片 URL）。MutationObserver 会读取 added/removed 节点及旧属性，保留同一任务内移除的临时副本线索；`connectedWhenCaptured: false` 的节点只保留文字证据，不会伪造它的布局测量。

如果公众号的插件插入流程没有派发浏览器 `paste` 事件，可在每次插入前手动标记阶段：

```javascript
__md2wxDiagnostic.beginPhase('原样')
// 粘贴并触发检测后，在下一次插入前：
__md2wxDiagnostic.beginPhase('简洁')
```

手动阶段会接收随后的一次粘贴，不会额外生成重复分组。上一组仍打开、未变化的弹窗不会直接算进下一组。若后一组没有采到弹窗或正文，会提示证据不足，**不表示“零告警通过”**。定时器从运行脚本起计算 90 秒；超过时间请重新运行，不会自动长期监听。停止或重新运行会移除粘贴监听器。

若自动识别仍选错正文，可以在开发者工具 **Elements** 面板选中文章外层容器，再回到 Console 执行 `__md2wxDiagnostic.inspect($0)`，最后重新下载报告。此操作只读，即使自动采集已停止也可补采；不要选择整个后台页面或弹窗。

临时标记只表示「被检测过」，不等同于违规；脚本不会把全部 `data-violation-id` 当成告警列表。

**隐私与边界**：数据只在当前浏览器内存和主动下载的本地文件中保存，不上传。报告含段落摘录（最多 70 字/项）及告警弹窗文字，回传前请检查。跨域 iframe、平台修改 DOM 选择器、已经消失的临时副本可能无法采集；没有找到正文时会明确提示，不会宣称检测通过。`stop()` 会撤销监听和定时器，不修改正文。重新运行脚本会先停止上一轮监听。

本地工具与后台探针共用扫描器；后台探针读取实际页面，不改动字体、样式、Range 方法或微信校验器。它用于采集证据，不是绕过官方检查。
